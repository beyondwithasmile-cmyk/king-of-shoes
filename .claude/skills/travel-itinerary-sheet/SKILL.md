# 旅行日程表シート

旅行ごとのタブに、数式で時刻が連鎖する日程表を書き込む。

これまでの書き込み先は Googleスプレッドシート **「二人旅行プラン」**
(`1aSnCEPtY3jEJi46jJ4pFUcYTAS-0zkrE9qRVv3Scjrw`)。ただし**これは既定値であって確定先ではない**。
別のスプレッドシートを使うこともあるので、毎回ユーザーに確認する。

## 絶対に守ること

1. **対象が確定するまで、何も調べない・何も書かない。** どの旅行の話か曖昧なまま
   メール検索やシートの読み書きを始めない。→「手順 0」
2. **既存のタブや `reference/` の実例を見て「次の旅行はこれだ」と決めつけない。**
   それらは過去の作業結果であって、いま頼まれている旅行とは限らない。
3. **ユーザーが指定したタブ以外には一切書き込まない。** 他タブの読み取りは可（文脈確認のため）。
4. **書き込み前に必ずバックアップを取る。** `itinerary.py backup` を先に実行する。
5. **行削除はしない。** 不要な範囲は `values.clear()` で内容だけ消す。
6. **`J1` / `Q1` の `=C1+1` / `=J1+1` を壊さない。** 2日目・3日目の日付はこの数式で連動する。
   日付は `C1` にだけ書き、他は触らない。
7. 書き込み後に必ず読み直して、各日の最終行の終了時刻を検証する。

## レイアウト契約

| 区分 | 列 |
|---|---|
| 1日目 | A=調整時間 B=所要時間 C=開始 D=－ E=終了 F=予定 |
| 空列 | G |
| 2日目 | H=調整時間 I=所要時間 J=開始 K=－ L=終了 M=予定 |
| 空列 | N |
| 3日目 | O=調整時間 P=所要時間 Q=開始 R=－ S=終了 T=予定 |

- データは **2行目から**。1行目はヘッダー（`C1`=日付、`F1`/`M1`/`T1`=各日のタイトル）。
- `D`・`K`・`R` 列は全行 **`－`（U+FF0D 全角ハイフンマイナス）**。ASCIIの `-` ではない。
- 4日目以降が必要なら列を右に6列ずつ＋空列1列で増やす（V〜AA など）。

## 時刻は値ではなく数式で連鎖させる

各日の**2行目の開始セルだけ**がリテラル。以降はすべて前行から計算する。

```
開始(各日の先頭行) : ="0905"                      ← 文字列リテラル。数値 905 にはしない
開始(2行目以降)    : =TEXT(MOD(TIME(VALUE(LEFT(前行の終了,2)),VALUE(RIGHT(前行の終了,2)),0)+当行の調整/1440,1),"hhmm")
終了(全行)         : =TEXT(MOD(TIME(VALUE(LEFT(当行の開始,2)),VALUE(RIGHT(当行の開始,2)),0)+当行の所要/1440,1),"hhmm")
```

- `="0905"` と書くのは `LEFT()`/`RIGHT()` が文字列を要求するため。数値 `905` だと `LEFT` が `"90"` を返して壊れる。
- `MOD(...,1)` により日跨ぎ（24時超え）も正しく丸まる。
- **調整時間 = その予定の前に置く空き時間**（移動の余裕・搭乗待ちなど）。所要時間はその予定自体の長さ。

## 空港ブロック（往路も復路も同じ形）

1日目の先頭は必ずこの4行で始める。5行目以降が現地の予定になる。

| # | 予定 | 調整 | 所要 | 終了時点 |
|---|---|---|---|---|
| 1 | 起床・準備・自宅出発 | 0 | **60** | 自宅出発時刻 |
| 2 | 自宅→〇〇空港 第N ターミナル | 0 | 実測値 | **ターミナル到着** |
| 3 | チェックイン・保安検査・ラウンジ | 0 | lead−30 | **出発時刻の30分前** |
| 4 | フライト 〇〇→〇〇 | **30** | 飛行時間 | **現地空港 到着時刻** |

`lead`（ターミナルに何分前に着くか）:

- **国内線 = 120分前**
- **国際線 = 180分前**

逆算:

```
ターミナル到着 = 出発時刻 − lead
ラウンジ滞在   = lead − 30        （国内線 90分 / 国際線 150分）
自宅出発       = ターミナル到着 − 移動時間
起床           = 自宅出発 − 60    ← これが C2 のリテラル値になる
フライト行      = 調整30分（搭乗）＋ 所要=飛行時間 → 終了が現地到着時刻に一致する
```

フライト行の調整30分が「出発30分前〜出発時刻」の搭乗時間にあたる。これにより
ラウンジ行の終了（出発30分前）とフライト行の開始（出発時刻）が自然につながる。

### 最終日（復路）も同じ形にする

**復路を「空港 発 ◯◯:◯◯」の1行で済ませない。** 往路と同じ2行にする。
spec のその日に `boarding` を書くと、rows の末尾に自動で足される。

| # | 予定 | 調整 | 所要 | 終了時点 |
|---|---|---|---|---|
| 1 | チェックイン・保安検査・ラウンジ | 0 | lead−30 | **出発時刻の30分前** |
| 2 | フライト 〇〇→〇〇 | **30** | 飛行時間 | **到着空港の到着時刻** |

最終日はその日の最終行が「復路の到着時刻」になる（例: 羽田着 16:00）。
出発時刻で終わらせない。復路の便も予約メールから取る。

`lead_minutes` でリード時間を上書きできる。ユーザーが「空港に1時間30分前」と
指定したらルールの120分ではなく `"lead_minutes": 90` を書く。

### 始発が2時間前に間に合わないとき

早朝便では公共交通の始発でもターミナル到着がリード時間に届かないことがある。
その場合は推測で丸めず、**実際に到着できる時刻を `terminal_arrival` に明示する**。
ラウンジ滞在は `出発30分前 − 実到着` で自動的に縮み、起床もそこから逆算される。
ルールに何分届かないかは `apply` の出力に表示されるので、ユーザーに必ず伝える。

タクシーに切り替えればルールを満たせる場合は、両案の起床時刻と料金を示して
ユーザーに選ばせる。どちらを採るかは勝手に決めない。

## レンタカーの受取・返却

**「空港店」という名前でも、ほぼ必ず空港の敷地外にある。** ターミナル直結と決めつけない。
レンタカー予約メール（じゃらんレンタカー等）から次を取る。

- 営業所名・**住所**・電話番号・営業時間
- 受取日時 / 返却日時（予約されている時刻）

住所が空港の住所と違えば敷地外。営業所の公式ページで**送迎の有無と空港からの所要時間**を確認する。

到着時刻の基準は**空港ターミナルに着く時刻**であって、営業所に着く時刻ではない。
返却側は最終日の便から逆算してこの順に積む。

```
空港ターミナル着 ＝ 出発時刻 − 指定のリード時間
  ← 送迎車（乗車時間＋待ち。空港到着側は巡回待ちが最大15分になる会社もある）
  ← 返却・精算（20分程度）
  ← 給油（満タン返し。営業所周辺のGSに寄る時間を必ず入れる）
  ← 営業所までの走行
```

- 営業所には**予約された返却時刻より前に着く**ように組む。早く返すのは問題ない。
- 受取側も同様に、到着便→手荷物受取→送迎→手続きの時間を見る。
- 逆算した結果その日の開始が早まるときは、観光の所要時間を勝手に削らない。
  **起床時刻を前倒しして全予定を保ち、何分早まったかをユーザーに伝える**。
  予定を削る判断はユーザーにさせる。

## 飲食店の提案（昼・夜）

昼食・夕食の枠を作るとき、店が決まっていなければ**ミシュランガイド掲載店から提案する**。
ユーザーが既に指定した店は動かさない。

### 対象にする店

**過去にミシュランガイドに掲載された店。**本編・地方特別版のどちらでもよく、年度も問わない。
3区分すべて対象にする。

| 区分 | 意味 | 価格の目安 |
|---|---|---|
| 星付き ★〜★★★ | 料理そのものの評価 | 夜15,000円〜が中心。昼だけ手頃な店もある |
| ビブグルマン | 価格以上の満足が得られる店 | 5,000円以下 |
| セレクテッド（プレート） | 調査員が薦める良店 | 幅広い |

評価は「素材の質／調理技術と味付け／独創性／コストパフォーマンス／一貫性」の5観点。

### 掲載は必ず確認する。推測で「ミシュラン」と書かない

**これは絶対。** 記憶や店の格から判断せず、毎回ウェブで確認し、
**どの版・何年度・どの区分**かまで特定する。特定できない店をミシュラン掲載として出さない。
紹介したいなら「ミシュラン掲載ではないが」と明記して別枠で出す。

### 掲載が無い地域は正直に言う

日本版は全国網羅ではない。東京・京都・大阪などの定期版と、地方の特別版で構成される。
**訪問先に版が存在しないことは普通にある。**

- 九州の例: 熊本・大分2018特別版、福岡・佐賀・長崎2019特別版 は存在する。
  一方**鹿児島単独の版は確認できない**。
- 版が無い地域で無理に候補をひねり出さない。「この地域はガイドの対象外」とそのまま伝える。
- 代替の基準（食べログ百名店、地元の名店、郷土料理の専門店）を出してよいが、
  **ミシュランとは明確に区別して示す**。

### 出し方 — 価格帯 × ジャンル

枠ごと（日付・昼/夜ごと）に表で整理し、1枠あたり3〜5軒。

価格帯（1人あたり・税込目安）: `〜3,000円` / `3,000〜6,000円` / `6,000〜15,000円` / `15,000円〜`
**昼と夜で価格が大きく変わる**ので、その枠の時間帯の価格を書く。

ジャンル例: 寿司・日本料理・郷土料理・焼肉・ラーメン・フレンチ・イタリアン・中華・うなぎ・蕎麦

各候補に必ず添えるもの:

- 店名／区分（★の数・ビブグルマン・セレクテッド）／**掲載版と年度**
- ジャンル／その時間帯の価格帯
- **旅行日に営業しているか**（曜日で定休日を確認・ランチ営業の有無・ラストオーダー）
- **予約の要否とリードタイム**（星付きは数週間〜数ヶ月前が普通）
- 直前・直後の予定からの移動時間

### 採用が決まってからの実務

提案して終わりにしない。入れる店が決まったら:

1. 旅行日の曜日が定休日でないか確認する
2. ランチ営業があるか確認する（星付きは夜のみが多い）
3. 入店ラストオーダーを予定テキストに書く（前の予定が押すと入れない）
4. 前後の移動を別行として入れる
5. rows に `"meal"` タグを付ける（予定セルが黄緑になる）
6. 予定テキストは `店名。食べるもの ※要予約・入店ラスト◯◯:◯◯` の形にする

### 決めるのはユーザー

候補を並べるところまでが仕事。**勝手に1軒に決めて旅程に入れない。**
既にユーザーが決めている店を、より格上の店に差し替えない。

## 書式ルール

`apply` は毎回シートの書式を作り直す。**手作業で塗った色は spec に書かない限り消える**ので、
ユーザーが手で色を付けていたら、それを spec のタグに写してから実行する。

| 対象 | 範囲 | 色 |
|---|---|---|
| 1行目のヘッダー | 既存のまま | 黄色 `#FFFF00`（触らない） |
| フライト行 | **開始・－・終了 の3セルだけ** | 水色 `#00FFFF` |
| 食事 | **予定セルだけ** | 黄緑 `#00FF00` |
| それ以外（2行目以降） | 全セル | 白（＝網掛けなし） |

- フライト行で色を塗るのは時刻の3列のみ。調整時間・所要時間・予定は塗らない。
- 下線は**シート全体から削除**する（太字・フォント・文字色はそのまま）。
- 網掛けは「白に戻してから塗り直す」順で1回の `batchUpdate` にまとめる。

### 揃えは必ず明示する

| 列 | 揃え |
|---|---|
| 調整時間・所要時間・開始・－・終了 | **中央** |
| 予定 | **左** |

**既定に任せない。** Googleスプレッドシートは数値を右、文字列を左に寄せるので、
放置すると調整/所要（数値）と開始/終了（`TEXT()` の戻り値＝文字列）で
必ず揃えがバラバラになる。見た目がガタガタになり、ユーザーから指摘される。

行を足したときも崩れないよう、データ行だけでなく**クリア範囲の末尾まで**
（既定では200行目まで）一括で指定する。1行目のヘッダーは対象外。

### タグの付け方

`rows` の各要素に4つ目の要素としてタグを足す。省略すれば無色。

```json
[10, 70, "菅乃屋 銀座通り店。馬刺し ※要予約", "meal"]
[0, 20, "鹿児島空港 発 14:15", "flight"]
```

`departure` から生成されるフライト行には `flight` が自動で付く。
復路や最終日の「空港 発 ◯◯:◯◯」のように手で書いた便の行には、自分で `flight` を付ける。

**`meal` にするもの** — 店名・施設名があって、そこで食べる/飲むのが目的の行。
食事だけでなくカフェ・スイーツも含む（例: 天文館むじゃき。しろくま）。

**`meal` にしないもの** — 土産や買い物が目的の行（例: 道の駅 山川港。朝市・土産、
森からし蓮根 本店。からしれんこん土産）、食事が他の用事のついでに入っている行
（例: 起床・準備・朝食、搭乗手続き・保安検査・昼食）。
迷ったらユーザーに確認する。勝手に広げない。

## 予定に Google マップのリンクを埋める

場所のある予定には、**予定テキストの店名・地名の部分だけ**に Google マップのリンクを張る。

**セル全体をリンクにしない。** `=HYPERLINK()` を使うと `※要予約・ラスト13:45` のような
注記まで巻き込まれて読みにくい。Sheets API の `textFormatRuns` で部分リンクにする
（本文はそのまま、指定した文字だけが青＋下線のリンクになる）。

### 書き方

`rows` の5要素目に指定する。4要素目（書式タグ）が無い行は `null` を置く。

```json
[0, 80, "熊本城 ※最終入園16:00", null, ["熊本城", "熊本城 熊本市中央区"]]
[10, 70, "菅乃屋 銀座通り店。馬刺し", "meal", ["菅乃屋 銀座通り店", "菅乃屋 銀座通り店 熊本市中央区"]]
```

- `["リンクにする部分文字列", "地図の検索クエリ"]`。文字列1つだけなら両方に使う
- **部分文字列は本文にそのまま含まれていること。** 見つからなければエラーで止まる
  （黙って位置がずれると気付けないため、わざと失敗させている）
- 検索クエリには**市区町村や住所を足す**。同名の店・神社は全国にあり、店名だけだと別の場所に飛ぶ
- URL は `https://www.google.com/maps/search/?api=1&query=<URLエンコード>`。
  検索形式なので存在しないページにはならない。場所IDを推測で書かない
- `departure` ブロックの移動行には `transit_map` で指定する

### どの行に張るか

- **滞在する行** → その施設・店
- **移動の行** → 行き先（ナビの起点にできる）
- **張らない行** — 起床・チェックアウト・レンタカー返却のような場所を特定しない行、
  「熊本市→鹿児島市」のような市単位の移動、シャトルバスの行

リンクは値を書き込むと消えるので、**必ず値を書いたあとに適用する**。`apply` はこの順を守っている。

## 手順

### 0. 対象を確認する（これより先に何もしない）

「旅行の予定」「旅行プラン」のように**対象が書かれていない依頼で呼ばれることが多い。**
その場合は**まず質問する。** Gmailを検索しない。シートを開かない。既存の旅程を要約しない。

聞くこと:

1. **どのスプレッドシートか** —「二人旅行プラン」でよければそのまま、違えばURLかIDをもらう
2. **どのタブか** — 新しい旅行なら新規タブ名（例 `熊本鹿児島2610`）、既存の旅行ならそのタブ名
3. **いつ・どこへの旅行か** — 日付と行き先

**会話の中でこれらが既に決まっている場合だけ、質問を飛ばしてよい。**
直前まで同じ旅行の話をしていた、ユーザーがタブ名やURLを書いた、という場合がこれにあたる。
セッションをまたいで「前回の続き」と推測するのは不可。

やってはいけない例:

- 呼ばれた直後にGmailで航空券を検索し、見つかった便から旅行を特定する
- `reference/` にある実例の旅行を「次の旅行」として報告する
- 既存タブの中身を読んで「次の旅行は◯月◯日の◯◯旅行です」と決めつける

### 1. 便情報を予約メールから取得する（推測しない）

Gmailコネクタで航空券の予約確認メールを検索し、**そこから**読み取る。

検索語の例: `熊本 航空券`、`eチケット`、`ANA 予約確認`、`JAL eチケットお客様控え`、
`搭乗案内`、旅行日（`2026/10/7`）、予約番号。

読み取る項目:

- 航空会社・便名
- **出発空港と出発ターミナル**（第1/第2/第3。JAL系=第1、ANA系=第2 が多いが**メールの記載を優先**）
- 出発時刻・到着時刻（→ 飛行時間 = 到着 − 出発）
- 国内線 / 国際線

**Gmailが使えない場合は推測で埋めない。** ユーザーに便名・出発時刻・到着時刻・ターミナルを聞く。
往路だけでなく復路の便も同じ要領で確認し、最終日の空港到着・搭乗手続きの時刻に反映する。

### 2. 自宅→ターミナルの移動時間を Yahoo!乗換案内で実測する

**旅行当日の日付・時刻で**検索する。平日/休日や早朝の始発有無で所要時間が変わるため、
「だいたい45分」のような概算は使わない。

```
https://transit.yahoo.co.jp/search/result?from=<出発地>&to=<到着地>&y=YYYY&m=MM&d=DD&hh=HH&m1=<分の十の位>&m2=<分の一の位>&type=1
```

- `from` / `to` は URL エンコードした日本語駅名。到着側は `羽田空港第2ターミナル` のように**ターミナルまで**指定する。
- `m1` `m2` は分を1桁ずつ分解する（05分 → `m1=0&m2=5`、15分 → `m1=1&m2=5`）。
- **`type=1` = 出発時刻指定。これを使う。** `type=2`/`4` は終電、`type=3` は始発が返り、到着時刻指定にはならない（検証済み）。
- 到着時刻から逆算したいときは、目標到着時刻の60〜90分前を `hh/m1/m2` に入れて `type=1` で検索し、
  **到着がターミナル到着期限を超えない最も遅い候補**を選ぶ。1〜2回の再検索で確定する。
- 採用した所要時間は分単位でそのまま使い、根拠（検索した日時・経路・到着時刻）をユーザーに報告する。
- 早朝便で始発が間に合わない場合はその旨を必ず伝える（タクシー前提なら所要時間を別途確認する）。

### 3. spec を書いて適用する

`scripts/itinerary.py` に渡す JSON を作る。

- `reference/spec-example.json` — 全フィールドの見本（`departure` ブロック付き）
- `reference/kumamoto-kagoshima-2610.json` — 実例（熊本鹿児島 2026/10/7-9）

```bash
python3 scripts/itinerary.py backup --spec spec.json --out ./backup
python3 scripts/itinerary.py apply  --spec spec.json
python3 scripts/itinerary.py verify --spec spec.json
```

`apply` は次をまとめて行う:

1. 出発ブロック（`departure` があれば）を1日目の先頭に生成し、C2 のリテラル開始時刻を逆算
2. `A2:T{最終行}` に数式込みで書き込み（`USER_ENTERED`）
3. その下（既定 200行目まで）を `values.clear()`
4. `C1` に日付、`F1`/`M1`/`T1` にタイトル（`J1`/`Q1` は触らない）
5. **2行目以降の背景色を白にリセット**（網掛けは1行目の黄色だけ残す）

### 4. 検証する

`verify` が各日の最終行の終了時刻を出力する。想定とずれたら数式の参照行がずれている。
ユーザーに「1日目 E{n}=◯◯◯◯」の形で報告する。

## 予定テキストの書き方

- 移動行は `A→B（車50分）` / `A→B（電車25分）` のように手段と時間を括弧で添える。
- 営業時間・予約・締切は `※` で続ける。例: `熊本城 ※最終入園16:00・天守登閣16:30`
- 店・施設は正式名称＋何をするかを `。` でつなぐ。例: `菅乃屋 銀座通り店。馬刺し`

